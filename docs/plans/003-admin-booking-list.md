# 003 — Implementation plan: Admin booking-request list

Spec: docs/specs/003-admin-booking-list.md

## Approach

This is a read/update view over 002's `booking_requests` table plus the minimum
authentication to gate it. The booking logic already exists; the work here is
containing the same health information (`reason`) inside an authenticated
surface, and doing so in a way a later change cannot quietly undo. Reception
identity is not new either — the existing `users` table (email + name, no
password, no role) is exactly a named-person allowlist, so membership in `users`
*is* the allowlist. It is maintained out of band (insert a row), matching the
spec's "no self-registration."

Three structural decisions carry the privacy and auth requirements so a careless
later change cannot reopen them:

1. **`reason` has exactly one exit and the projections cannot carry it.** The
   list and detail response schemas in `packages/shared/src/admin.ts` have no
   `reason` field at all, so no query result can accidentally include it
   (compile-time, mirroring 002's whitelist). The reason is returned only by one
   dedicated `reveal` action — a POST with `Cache-Control: no-store` — and never
   logged. This is the AC7 guarantee expressed in the type system, not in review
   discipline.
2. **Authentication is a capability check inside every data handler, not a
   route-level guard.** A single `requireAdmin(req)` reads the session cookie,
   enforces the idle timeout, and returns the acting user or throws 401. Every
   admin handler calls it first and takes the returned actor; there is no admin
   code path that returns a request without it (AC1/AC10). A new endpoint that
   forgets it does not compile against the store, which requires an actor id.
3. **Secrets live only as hashes and every mutation is attributable and
   versioned.** Magic-link tokens and session cookies are stored as SHA-256
   hashes (same pattern as `sourceHash`), so a DB dump cannot be replayed into a
   session. Each status change records actor + time and bumps a `version`;
   updates are `WHERE version = expected`, so two reception users cannot silently
   overwrite each other (AC13), and deletes write an audit row that copies the
   reference but never the reason (AC8).

Passwordless magic-link + server-side sessions is the spec-mandated shape, not a
novel choice. Tokens and sessions live in Postgres for the same reason 002's
rate limiting does: serverless has no shared memory.

## Database changes

Expand-only. New tables plus additive columns; nothing dropped or tightened.

```sql
-- reception identity/allowlist = existing users table (reused, unchanged)

CREATE TABLE auth_tokens (            -- single-use magic links
  id          uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id     uuid NOT NULL REFERENCES users(id),
  token_hash  text NOT NULL UNIQUE,  -- sha256(raw); raw never stored
  expires_at  timestamptz NOT NULL,
  consumed_at timestamptz,           -- set on first use → single-use
  created_at  timestamptz NOT NULL DEFAULT now()
);
CREATE TABLE sessions (
  id                 uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id            uuid NOT NULL REFERENCES users(id),
  token_hash         text NOT NULL UNIQUE,
  last_seen_at       timestamptz NOT NULL DEFAULT now(),  -- idle-timeout basis
  absolute_expires_at timestamptz NOT NULL,
  revoked_at         timestamptz,
  created_at         timestamptz NOT NULL DEFAULT now()
);
CREATE TABLE admin_audit (           -- attribution; never holds reason
  id          uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  actor_id    uuid NOT NULL REFERENCES users(id),
  action      text NOT NULL,         -- 'status_change' | 'delete'
  reference   text NOT NULL,         -- copied so it survives the row's deletion
  request_id  uuid,                  -- null after delete
  from_status text,
  to_status   text,
  at          timestamptz NOT NULL DEFAULT now()
);

ALTER TABLE booking_requests
  ADD COLUMN internal_note      text,          -- nullable, bounded in app
  ADD COLUMN last_actioned_by   uuid REFERENCES users(id),  -- nullable
  ADD COLUMN status_updated_at  timestamptz,   -- nullable
  ADD COLUMN version            integer NOT NULL DEFAULT 0;  -- concurrency token
```

**This is the only PR in the sequence; no contract PR follows.** Every change is
backwards compatible with the currently deployed 002 code: the new tables are
unreferenced by it, and the new columns are either nullable or `NOT NULL DEFAULT`
so 002's insert (which names none of them) keeps working. `version NOT NULL
DEFAULT 0` is safe on the existing table because the default backfills in the
same statement. Nothing is read-then-dropped, so there is no expand/contract
split to schedule.

## API contract

All admin endpoints call `requireAdmin` first → 401
`{ error: { code: 'UNAUTHENTICATED' } }` when the session is missing, idle-expired,
or revoked. Actor is the returned user.

`POST /api/admin-auth?action=request` `{ email }` → **always** 200 `{ ok: true }`
(sends a link only if the email is in `users`; identical response otherwise — AC2).
`POST /api/admin-auth?action=verify` `{ token }` → 200 `{ email, name }` + sets
`admin_session` cookie (HttpOnly, Secure, SameSite=Strict); 401 if token is
unknown, expired, or already consumed (AC3). `POST ?action=signout` → 204, clears
cookie. `GET ?action=me` → 200 `{ email, name }` | 401.

`GET /api/admin-requests?cursor=&limit=` → 200 `{ items: AdminRequestListItem[],
nextCursor: string | null }`, non-purged (`purge_after > now`), keyset-ordered by
arrival time (newest-first), **no `reason` field** (AC4). Query is
`pageQuerySchema` (cursor optional, `limit` default 20, ceiling 100) and the
response is `pageResponseSchema(adminRequestListItemSchema)`, both imported
unchanged from `packages/shared/src/pagination.ts`; the cursor encodes
`(created_at, id)` so pages neither duplicate nor skip rows when requests arrive
or are purged between loads, and `nextCursor` is null on the last page (AC14).
`POST /api/admin-requests` `{ action: 'reveal', id }` → 200 `{ reason: string | null }`,
`Cache-Control: no-store` (AC7).
`PATCH /api/admin-requests?id=` `{ status?, note?, expectedVersion }` → 200 detail
with new version; 409 `{ error: { code: 'CONFLICT' }, current }` on stale version
(AC13); 404 `NOT_FOUND` if purged mid-session. Setting `contacted` stamps
`contacted_at` (AC6); every change sets `last_actioned_by` + `status_updated_at`
and writes an `admin_audit` row (AC5).
`DELETE /api/admin-requests?id=` → 204; writes a `delete` audit row (actor +
reference + time, no reason) then removes the booking row (AC8).

Response schemas live in `packages/shared/src/admin.ts`; the frontend parses with
the same schema the server validates against. Constants: `MAGIC_LINK_TTL_MINUTES`,
`SESSION_IDLE_MINUTES`, `SESSION_ABSOLUTE_HOURS`, `NOTE_MAX`.

the consumed-token test.

## Rollback

Revert the deploy. The migration is safe to leave applied: the new tables and
columns are inert to 002/005 code, so a reverted frontend/api simply stops using
them. If the tables must go (they hold session material and an audit trail, not
patient health data — `reason` is never copied into them), drop `admin_audit`,
`sessions`, `auth_tokens` and the four `booking_requests` columns; no health
information is lost because none is stored there.

## Risks

1. **The magic-link email cannot actually be delivered.** The repo has no mailer
   and no email provider — 002's `notify` was left as an unimplemented seam. If
   the send silently fails, reception is locked out with no signal. Mitigated by
   putting the transport behind `mailer.ts` (a `fetch`-based seam configured by
   env, so tests inject a fake and no npm dependency is added) and by a test that
   asserts a link is generated and the send is attempted. **The concrete provider
   and its env config are an ops prerequisite and a launch blocker** — the spec's
   "Prerequisite — email delivery does not yet exist" section now formally
   documents this, so it is a recorded requirement rather than an architect's
   unilateral flag; selecting the provider likely wants an ADR in
   `docs/decisions/`.
2. **Session/token theft.** Mitigated by hash-at-rest for both token and session,
   HttpOnly + Secure + SameSite=Strict cookie, single-use links, and dual idle +
   absolute expiry enforced server-side on every request.
3. **`reason` leaking through the new endpoints.** Lower than in 002 because the
   list/detail schemas structurally omit it and reveal is the single exit, but it
   is the reviewer's first check. The never-leaks test asserts a distinctive
   reason string appears in neither the list response nor captured logs.

## Not doing

Search, filter, and richer sort beyond the keyset arrival-time order,
in-app allowlist management, patient access/correction requests, throughput
metrics, and SMS/new-arrival notification — all deferred by the spec. The purge
job remains spec 004. This plan does not modify `booking-requests.ts`;
reconciling that handler is spec 005.
