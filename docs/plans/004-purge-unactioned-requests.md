# 004 — Implementation plan: Purge of expired booking requests

Spec: docs/specs/004-purge-unactioned-requests.md

## Approach

One secret-guarded cron endpoint that deletes expired `booking_requests` rows in
bounded, independently-committed batches and leaves exactly one non-identifying
summary row in `admin_audit`. There is no new table, no soft-delete, and no
patient-facing surface — the work is entirely in getting the eligibility rule and
the failure/idempotency behaviour right without ever reading `reason`.

Three structural decisions carry the privacy and correctness requirements:

1. **Eligibility is one pure, exhaustively-tested function, not a clever SQL
   predicate.** `purgeDecision(row, now)` in `packages/shared/src/purge.ts`
   returns `'unactioned' | 'actioned' | 'keep'` from `{ status, purgeAfter,
   statusUpdatedAt, contactedAt }` — never `reason`. Both retention clocks and
   the "never delete on ambiguous timing" default live in that one function, so
   AC2/AC3/AC4 and the null-timestamp edge are pinned by unit tests with no
   database harness. The store's SQL is a thin, index-backed prefilter; the pure
   function is the authoritative arbiter of every deletion.
2. **`reason` is structurally unreadable by this job.** The candidate projection
   selects only the four eligibility fields (never `reason`), the delete is
   `DELETE ... WHERE id = ANY($ids)`, and the audit row holds only counts and a
   timestamp. There is no code path in which a `reason` value enters memory, a
   log, or the audit table (AC7, privacy req 2/3).
3. **Every batch commits on its own and the audit is written once at the end.**
   A mid-run crash leaves already-deleted rows deleted and writes no audit row;
   the next scheduled run re-selects whatever remains. Selection excludes rows
   already gone, so nothing is deleted twice (AC9). A per-run ceiling bounds the
   invocation to its time budget (AC12).

Observability comes for free from the design: each successful run leaves a
timestamped `purge_run` audit row and the endpoint returns the same counts, so
"when did retention last run" is queryable and a missing recent row is the
detectable signal of a disabled scheduler. Alerting on that absence is out of
scope per the spec.

**The actioned-clock anchor — the architect's call.** "The moment it was
actioned" reads from `COALESCE(status_updated_at, contacted_at)`.
`status_updated_at` (added by 003, set on *every* status transition) is
authoritative and covers `scheduled`/`declined`, which `contacted_at` does not.
`contacted_at` (002, exists today) is the fallback and honours the spec's "or a
contact timestamp is recorded" wording. If **both** are null on a non-`pending`
row the anchor is undefined, so `purgeDecision` returns `keep` — the spec's
never-delete-on-ambiguous-timing rule.

## Sequencing dependency on spec 003 — read before implementing

This job **depends on 003's schema and must ship after it.** Specifically:

- **`admin_audit` table (003)** — the required summary record has nowhere to go
  without it. This is the hard dependency; 004 cannot function before 003.
- **`status_updated_at` column (003)** — the primary actioned-clock anchor.

It does **not** use 003's `last_actioned_by` or `version`. Its 30-day clock is
also effectively dormant until 003 ships, because nothing can move a row off
`pending` before the admin UI exists — so before 003 there are no actioned rows
to purge anyway, only the 002 `pending`/`purgeAfter` clock.

Because 004's migration is `0002` (after 003's `0001`) in Drizzle's linear
journal, and 004's `schema.ts` edit *alters the `admin_audit` definition 003
introduces*, the ordering is enforced by the migration tooling: **if someone
attempts to ship 004 before 003, the migration and the schema edit fail loudly
(the objects do not exist) rather than silently mis-purging.** That loud failure
is the intended safety behaviour. This plan is written assuming 003 has merged;
`contacted_at` is the fallback only, not a substitute that lets 004 stand alone.

## Database changes

Expand-only, on 003's `admin_audit`. No new table; `booking_requests` is
unchanged (this job reads existing columns plus 003's `status_updated_at`).

```sql
-- admin_audit was created by 003 for per-request status_change/delete events.
-- 004 generalises it to also hold one system-written run summary.
ALTER TABLE admin_audit
  ALTER COLUMN actor_id  DROP NOT NULL,   -- a system run has no user actor
  ALTER COLUMN reference DROP NOT NULL,   -- a run summary names no request
  ADD COLUMN deleted_unactioned integer,  -- set only on purge_run rows
  ADD COLUMN deleted_actioned   integer;
-- `action` is plain text (not a pg enum); the new value 'purge_run' needs no DDL.
```

A `purge_run` row is `action='purge_run'`, `actor_id=NULL` (means system),
`request_id=NULL`, `reference=NULL`, the two counts set, `at=now()`. Because
`request_id` is null it never appears in an admin request's history view (003),
so the two features do not interfere.

**This is the PR after 003 and it is backwards compatible with 003's
admin-list code**, which always supplies `actor_id` + `reference` and ignores the
new nullable columns. Dropping `NOT NULL` never breaks an existing row or an
insert that still provides a value; the added columns are nullable. Nothing is
read-then-dropped, so there is no contract PR to follow.

## API contract

`GET /api/purge` — internal, scheduler-only. Not linked from any client.

- Auth: requires `Authorization: Bearer <CRON_SECRET>` (Vercel Cron convention,
  `CRON_SECRET` env). Missing/wrong → 401 `{ error: { code: 'UNAUTHENTICATED' } }`
  and **no deletion or selection occurs** (AC8). The secret check is the first
  statement in the handler, before any DB access.
- Success → 200 `purgeRunResultSchema`:
  `{ deletedUnactioned: number, deletedActioned: number, completed: boolean }`
  (`completed=false` when the per-run ceiling was hit and rows remain). The body
  is non-identifying — counts only (observability).
- Batch failure → 500 `{ error: { code: 'INTERNAL', requestId } }`; the error is
  logged by count + error string only, never row content. Already-committed
  batches stand; no audit row is written for a failed run.

`vercel.json` cron: `{ "path": "/api/purge", "schedule": "0 16 * * *" }` — 16:00
UTC ≈ 02:00 AEST, off-peak, daily.

## Test plan

All against a fake `PurgeStore` and the pure classifier — no DB harness, matching
the repo's existing handler-test style.

- AC1 -> `packages/shared/src/purge.test.ts::deletes a pending request past its purgeAfter`
- AC2 -> `packages/shared/src/purge.test.ts::deletes an actioned request more than 30 days after action even if purgeAfter is future`
- AC3 -> `packages/shared/src/purge.test.ts::keeps an actioned request actioned fewer than 30 days ago even if purgeAfter has passed`
- AC4 -> `packages/shared/src/purge.test.ts::keeps a pending request whose purgeAfter is in the future`
- AC5 -> `apps/api/routes/purge.test.ts::issues a hard delete by id and never an update (no soft-delete flag)`
- AC6 -> `apps/api/routes/purge.test.ts::writes exactly one system audit row with split counts and no identifiers`
- AC7 -> `apps/api/routes/purge.test.ts::never selects the reason column and it is absent from logs`
- AC8 -> `apps/api/routes/purge.test.ts::rejects a caller without the scheduler secret and deletes nothing`
- AC9 -> `apps/api/routes/purge.test.ts::deletes in bounded batches and resumes from the remainder after an interrupted run`
- AC10 -> `apps/api/routes/purge.test.ts::a run with no eligible rows completes and records a zero-count audit`
- AC11 -> `packages/shared/src/purge.test.ts::treats a non-pending row with a null action timestamp as keep` + `apps/api/routes/purge.test.ts::makes no write to surviving rows`
- AC12 -> `apps/api/routes/purge.test.ts::stops at the per-run ceiling and reports completed=false`

## Rollback

The 3am action is to **remove the `crons` entry (or unset `CRON_SECRET`) and
redeploy** — the job simply stops firing. Deletions already performed are
permanent by design; that is correct behaviour, not data loss to recover, because
every deleted row was past its committed retention date. The `admin_audit` ALTER
is safe to leave applied (all changes are relaxations or nullable additions).
There is deliberately no un-purge path.

## Risks

1. **A wrong eligibility rule deletes health data early — irreversible.** Highest
   severity in the repo. Mitigated by concentrating the rule in one pure function
   with exhaustive boundary tests (AC2/AC3/AC4 and the ambiguity default), the
   never-delete-on-undefined-anchor rule, and the per-run ceiling that caps the
   blast radius of any single bad run. The first production run should be
   inspected via its audit counts before the daily cadence is trusted.
2. **Shipping before 003.** `admin_audit` and `status_updated_at` would be
   missing. Mitigated by the enforced migration ordering (`0002` after `0001`)
   and the `schema.ts` edit targeting a 003-defined table — both fail loudly if
   003 has not merged, rather than running a degraded purge.
3. **Trigger reachable without the secret.** Mitigated by checking the Bearer
   secret as the first handler statement, returning 401 before any selection or
   delete, and relying on Vercel's cron protection. No deletion code runs on the
   reject path.
4. **Run exceeds the serverless budget.** Mitigated by fixed batch size, a
   per-run row ceiling, and `completed=false` handing the remainder to the next
   scheduled run (AC12) — correctness never depends on clearing the table in one
   invocation.

## Not doing

Configurable per-service or per-status retention, any restore/undo path (by
design impossible), purging the `admin_audit` rows themselves, and paging/alerting
on a missed run — the plan provides the observable signal (timestamped
`purge_run` rows + returned counts) but not the monitor that watches for its
absence. No change to 002/005 creation or 003 admin behaviour.
